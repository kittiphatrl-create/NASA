### 2. ทิศทางภาพและมิติของห้อง

ทำห้องแบบ cutaway 3/4 เห็นผนังตั้ง พื้น เพดาน/คานบางส่วน และกรอบประตู มีขอบเขตห้องจริง ตัวละครเดินเข้าไปด้านหลังห้องได้ ไม่ใช่ภาพ top-down ที่ทุกอย่างนอนแบนบนพื้น และไม่ใช่ทางเดินแนวนอนอย่างเดียว

แนะนำเริ่มด้วยฉาก 2.5D ที่ใช้ SpriteRenderer หลายชั้นในระบบเดิม: พื้น → ของด้านหลัง → ตัวละคร/เฟอร์นิเจอร์ที่เรียงตามตำแหน่งเท้า → กรอบประตู/ของด้านหน้า ใช้เงาสัมผัสและแสงช่วยให้วัตถุตั้งอยู่บนพื้น ห้ามแปลงเป็น 3D หรือเปลี่ยน render pipeline ทั้งโปรเจกต์เพียงเพื่อให้มีมิติ

ถ้าจำเป็นต้องใช้พื้นและผนัง 3D ให้ทดลองห้องเดียวก่อนและเทียบกับ layered 2D ด้วยภาพจริง โดยใช้เกณฑ์การอ่านทางเดิน การบังตัวละคร ความสอดคล้องของมุมกล้อง และต้นทุนการทำแอนิเมชัน เลือกจากผลทดลอง ไม่ตัดสินว่าเทคนิคหนึ่งสวยกว่าโดยอัตโนมัติ

- เริ่มห้องพัก/กินข้าวที่เชื่อม airlock เป็นชิ้นงานทดลองครบวงจรหนึ่งห้อง
- มีชั้นอาหาร น้ำ โต๊ะ เก้าอี้ ที่นอน อุปกรณ์ออกซิเจน และแหล่งไฟที่วางอย่างมีเหตุผล
- ทางเดินต้องอ่านออก วัตถุมี footprint กีดขวางจริง ตัวละครเดินอ้อมได้ ไม่ทะลุโต๊ะหรือประตู
- ผนังหน้าหรือของสูงที่บังผู้เล่นให้จางลงอย่างนุ่มนวล คืนค่าเมื่อเดินพ้น ห้ามจางทุกอย่างตลอดเวลา
- ใช้สีและความหนาเส้นสม่ำเสมอ; ถ้าคง pixel art ให้กำหนด pixel density/filter/pivot และขนาดภาพเดียวกัน ไม่ผสมภาพวาดละเอียดกับตัวละครพิกเซลเล็กจนหลุดชุด
- แสงฟ้าเย็นจากอุปกรณ์ตัดกับแสงอุ่นบริเวณโต๊ะ ใช้รอยซ่อม ความสกปรก และของใช้เล่าเรื่อง โดยไม่เพิ่มรายละเอียดจนจุดกดหาย

### 3. ตัวละครเดินและวิ่งหลายทิศ

- เดินบนระนาบพื้นสองแกนได้จริง รองรับการคลิกเดินตามระบบเดิมและคีย์บอร์ดหากมีอยู่แล้ว ปรับความเร็วทแยงให้ไม่เร็วเกินทิศตรง
- อย่างน้อยต้องมี front/back/left/right ที่เห็นต่างกัน เดินขึ้นห้องต้องเห็นหลังและเป้ ไม่ใช้ sprite ด้านข้างกลับซ้ายขวาแทนทุกทิศ
- ชุดขั้นต่ำ: idle 4 ทิศ, walk 4 ทิศ, run 4 ทิศ พร้อม action นั่งกิน/ดื่มและซ่อมตามจุดที่ใช้จริง ด้านซ้ายขวาสะท้อนได้เฉพาะเมื่ออุปกรณ์บนตัวและเงายอมรับได้
- ข้อเสนอเริ่มต้น walk/run 6–8 เฟรมต่อทิศ idle 2–4 เฟรม แล้วปรับจากภาพจริง ไม่ถือว่าแค่ bob ตัวขึ้นลงเป็นแอนิเมชันวิ่งสำเร็จ
- ช่วงเก็บของเร่งด่วนใช้ run; เดินปกติใช้ walk ให้ทิศหันสัมพันธ์กับเวกเตอร์เดิน หยุดแล้วคงทิศล่าสุด
- pivot อยู่ตำแหน่งเท้าคงที่ ไม่สั่นหรือไถลตอนเปลี่ยนเฟรม เงาตามพื้น และ depth sorting ตามเท้า ไม่ตามจุดกึ่งกลางหัว
- หากใช้ perspective ค่อยปรับขนาดตามความลึก; ถ้าใช้ orthographic ไม่ต้องบังคับย่อขยายจนดูผิดกล้อง

### 4. ฉากตาแมว First Person เป็นฟีเจอร์หลัก

ลำดับประสบการณ์: เสียงเคาะจากประตู → ผู้เล่นเดินไป airlock → คลิกตาแมว → กล้องดันเข้า/เฟดสั้น ๆ → มุมมองระดับสายตาผ่านตาแมวเต็มจอ → เห็นผู้มาเยือนอยู่ตรงหน้า → เลือกวิธีตรวจ → ได้หลักฐาน → ตัดสินใจเปิด/ปฏิเสธ/คุยต่อ → กลับฐานพร้อมผลที่เกิดจริง

มุมมองต้องรู้สึกว่าเราเอาตาแนบประตู: ขอบมืดวงกลมหรือ oval, ขอบเลนส์และ distortion เล็กน้อย, คนอยู่ระดับสายตาและเห็นสีหน้า/ช่วงตัว, ฉากดาวอังคารด้านนอกมีระยะลึก คนหายใจ กะพริบตา และขยับน้ำหนัก ไม่ใช่หน้าต่างการ์ดที่แปะภาพคนจิ๋ว ต้องมีช่วงเห็นตัวพอให้สแกนได้ และซูมใบหน้าได้โดยไม่ตัดหลักฐานสำคัญ

โครงจอแนะนำ:

```
[หลักฐานที่พบ / บันทึก ORBI]   [ผู้มาเยือนตรงหน้าในเลนส์]   [กลับ]
                              [คุย / infrared / ตรวจสัญญาณชีพ]
                              [ให้รอ / รับเข้าห้องกักกัน / ปฏิเสธ]
```

แยกการตรวจออกจากการตัดสินรับเข้าอย่างชัดเจน การคลิกคนคือเปิดฉากตรวจ ไม่ใช่เปิดประตูจริง ปิดฉากตรวจต้องไม่แอบรับใครเข้ามา

ตัวเลือกตรวจ:

1. **อินฟราเรด:** เครื่องสแกนยกเข้าจอ เส้นแดงกวาดจากหัวลงลำตัวราว 1–1.5 วินาที มี heat-map และเสียง; หลักฐานขึ้นด้านซ้ายเป็นข้อความสั้นและตำแหน่งที่ตรวจพบ เช่น อุณหภูมิต่ำผิดแบบมนุษย์ แต่ต้องบอกข้อจำกัดของเครื่องด้วย
2. **สัญญาณชีพ:** คลื่นหรือจังหวะกะพริบสัมพันธ์กับเสียง ได้ข้อมูลชีพจร/การหายใจที่อาจมีคำอธิบายหลายแบบ ไม่แจกคำตอบว่าเป็นศัตรูแน่นอน
3. **พูดคุย:** ผู้มาเยือนตอบคำถามเกี่ยวกับที่มา ความต้องการ และเหตุการณ์ที่ผ่านมา ผู้เล่นเทียบความสอดคล้องกับหลักฐานได้ ตรวจความเป็นมิตรผ่านพฤติกรรมและบทสนทนา ไม่ทำเครื่องวัดความดีที่รู้ทุกอย่าง
4. **ตรวจสิ่งของ/บาดแผล** เมื่อข้อมูลเหตุการณ์รองรับ ให้มีสภาพที่เห็นได้ตรงกับข้อมูล ไม่สร้างปุ่มหลอกที่ทุกครั้งตอบเหมือนกัน

ห้ามอ้างว่า infrared ตรวจเผ่าพันธุ์หรือเจตนาได้แน่นอน ผลเผ่าพันธุ์ใช้คำว่า “คาดว่า/ไม่พบในฐานข้อมูล” พร้อมความมั่นใจเมื่อมีฐานข้อมูลในโลกนิยาย แยก science fact ของ NASA ออกจากนิยายเอเลียนให้ชัด

- ผลสแกนต้องผูก visitor ID และ state จริง ไม่สุ่มข้อความใหม่ทุกครั้งจนหลักฐานขัดกัน
- มีตัวอย่างเพื่อนที่ดูน่าสงสัยแต่มีเหตุผล และผู้ไม่เป็นมิตรที่ต้องใช้หลักฐานมากกว่าหนึ่งอย่าง ผู้เล่นเรียนรู้ได้ ไม่แพ้จากคำตอบที่ไม่มีเบาะแส
- การตรวจเดิมซ้ำไม่หักทรัพยากรซ้ำโดยไม่บอก ถ้ามีต้นทุนหรือ cooldown ให้สื่อก่อนกด
- กัน double-click และ callback ซ้อนระหว่างสแกน ค่าใช้จ่ายลง simulation ครั้งเดียว; Esc/เปลี่ยนภาษา/ออกฉากไม่ทำให้ state หายหรือยกเลิกผลโดยผิดกติกา
- ระบุให้ชัดว่าเวลา simulation และเวลารอของแขกเดินต่อหรือพักเมื่ออ่านบทสนทนา เพื่อไม่ลงโทษคนอ่านภาษาไทยช้า

### 5. HUD เป็นภาพที่อ่านง่าย

มุมซ้ายบนเป็นกลุ่มเกจทรัพยากรหลัก เช่น O2 น้ำ และพลังงาน ใช้หลอดหรือถังที่มีระดับของเหลว/ประจุ มีไอคอนสติกเกอร์และชื่อสั้น ตัวเลขไม่แสดงเป็นค่าเริ่มต้น; เลือกทรัพยากรจาก simulation จริง ไม่เพิ่มหลอดใหม่ที่ไม่เชื่อมระบบ

มุมขวาบนเป็น portrait ตัวละคร สีหน้าและสภาพบอกสุขภาพ เหนื่อย หิว หรือป่วย มีชื่อสถานะสั้น ๆ กดเพื่อดูคำอธิบายเพิ่มเติม ต้องแยกสุขภาพกับอารมณ์ ไม่ใช้หน้ายิ้มตัวเดียวทำให้เข้าใจว่าทุกระบบดีหมด

- เกจควรเห็นระดับชัดภายในหนึ่งวินาที มีขีดแบ่ง รูปทรง และคำสถานะ ไม่พึ่งแดง/เขียวอย่างเดียว
- ระดับอันตรายมีเสียง/ภาพเตือนที่พอเหมาะ และมีตัวเลือกลด motion/ลดแสงกระพริบ
- เมื่อทำกิจกรรม เกจเปลี่ยนอย่างอ่านออก พร้อมตัวละครลงมือและเสียง ไม่ขึ้น floating text “O2 -2” เป็นประสบการณ์หลัก
- เก็บค่าจริงไว้ใน simulation/debug สำหรับทดสอบ; โหมดช่วยเหลือสามารถเปิดตัวเลข/ต้นทุนละเอียดได้
- อย่าทำให้ทุกหลอดดูเป็นน้ำ: O2 มีสัญลักษณ์ก๊าซ/ฟอง พลังงานมีประจุ น้ำมีผิวน้ำ เพื่อแยกประเภททันที

### 6. ซ่อนเลขต้นทุน แต่ไม่ซ่อนเหตุผล

ตัวเลือกหลักเขียนเป็นสิ่งที่ทำ เช่น “ออกไปตรวจแผงโซลาร์” แทน “เสีย O2 2 / เวลา 3 / ได้ไฟ 5” ใช้สัญลักษณ์และคำประมาณ เช่น ใช้อากาศน้อย/ใช้เวลานาน/เสี่ยงสูง พร้อมคำเตือนผลร้ายที่ผู้เล่นควรรู้ อย่าซ่อนว่าการออกนอกฐานต้องใช้ออกซิเจน

หลังเลือกให้มีเหตุ → การกระทำ → ผล: เสียงวาล์ว, ใส่หมวก, ตัวละครเดินไป, เกจ O2 ลด และแผงโซลาร์เปลี่ยนสภาพ; บันทึกสั้นอธิบายสิ่งที่เกิด ผู้เล่นจึงเรียนรู้จากผล ไม่ใช่สุ่มเสียทรัพยากรโดยไม่มีที่มา

งานชนิดเดียวกันภายใต้สภาพเดียวกันควรมีต้นทุนสม่ำเสมอ หากต้นทุนเปลี่ยนเพราะชุดรั่ว/สภาพอากาศ ให้เห็นหรือได้รับคำเตือนก่อน ไม่ทำความลึกลับด้วยการซ่อนกฎสำคัญทั้งหมด

ฉากกินข้าว: เดินไปโต๊ะ → เห็นอาหารและคนในฐาน → ลากหรือเลือกแบ่งส่วนอาหาร → เห็นส่วนอาหารบนจานและของบนชั้นลด → แอนิเมชันกิน/ดื่ม → สีหน้าและเกจเปลี่ยน การตัดสินใจแบ่งให้แขกต้องสะท้อนทั้งความสัมพันธ์และของที่เหลือ โดยไม่ลดทอนให้เป็นกล่องข้อความล้วน

### 7. อาหารและน้ำเป็นวัตถุที่มองเห็น

ชั้นเก็บของต้องสะท้อน inventory ตัวจริง อาหารลดหนึ่งส่วน ภาพบนชั้นลด/ระดับลด; ของหมดเห็นพื้นที่ว่าง ขวดน้ำเหลือน้อยต้องต่างจากเต็ม มีไอคอนจำนวนหรือกดตรวจได้เพื่อไม่ให้ผู้เล่นต้องนับพิกเซลเล็ก ๆ

หากเป็นค่าทรัพยากรต่อเนื่องให้แสดงเป็นกลุ่ม/ระดับที่กำหนด mapping ชัดเจน ไม่แอบตีความว่า sprite หนึ่งชิ้นเท่ากับหนึ่งหน่วยเสมอ หากหลายคนใช้พร้อมกันต้องอัปเดตจาก state เดียวกัน ห้ามภาพอาหารเป็นเพียงของตกแต่งที่ไม่เคยลด

### 8. การ์ดตัวเลือกที่น่ากด

แสดงครั้งละ 2–4 ใบ มีไอคอน ภาพย่อ ชื่อการกระทำ และคำบอกความเสี่ยงสั้น ๆ เมื่อ hover/focus การ์ดยกขึ้นเล็กน้อย ขยายราว 1.04–1.07 และเกิดแสงขอบ/เงาในเวลาประมาณ 120–180 ms เมื่อกดมี feedback และล็อกอินพุตจนรับคำสั่งสำเร็จ

- keyboard focus ต้องได้ feedback เทียบเท่า hover รองรับ Enter/Space; Tab ไม่หลงหลัง overlay
- การ์ด disabled ต้องบอกเหตุผล; ปุ่มเป้าหมายไม่ขยับหนีเคอร์เซอร์จาก layout reflow
- ไม่ให้ภาพยกการ์ดบังข้อความไทยหรือการ์ดข้าง ๆ; click target คงที่และมี clipping ที่ถูกต้อง
- เคารพ reduced motion ใช้ไฮไลต์แทนการเด้ง; SFX ไม่ดังซ้ำทุกเฟรม

### 9. ขอบเขตและลำดับทำงาน

เริ่มด้วย vertical slice ที่เล่นได้จริง: ห้องโต๊ะอาหารเชื่อมประตูหนึ่งห้อง, ตัวละครสี่ทิศพร้อมวิ่ง, HUD ภาพ, แขกหนึ่งเหตุการณ์ที่มีหลายผล, ตรวจ infrared + คุย + รับ/ปฏิเสธ, กินอาหารแล้วของลดจริง ทดสอบวงจรนี้ก่อนขยายทุกห้อง

ส่งภาพ before/after ของห้อง, ฉากตาแมว, สแกน, hover card, ชั้นอาหารก่อน/หลัง และตัวละครหันหลังระหว่างวิ่ง พร้อมวิดีโอ runtime สั้นเมื่อเครื่องมือบันทึกได้ ถ้าทำไม่ได้ให้บอกตรง ๆ ห้ามเรียกภาพคอนเซปต์ว่าภาพ runtime

หากไม่มี sprite ที่ใช้ได้ ให้สร้างงานต้นแบบที่มีทิศและเฟรมครบและระบุว่าเป็น placeholder; ใช้ imagegen สำหรับ concept/portrait เมื่อเหมาะสม แต่ห้ามสมมติว่า sprite sheet ที่สร้างครั้งเดียวมี pivot และ animation ต่อเนื่องถูกต้องโดยไม่ตรวจ ห้ามนำภาพเกมอ้างอิงมาแปะในเกมเรา

### 10. เกณฑ์ยอมรับและการตรวจ

- รัน Main.unity ได้ และจบ flow เดิมที่เกี่ยวข้องได้ ไม่พัง save/วันเวลา/การช่วยเหลือ
- เดินเข้าลึกเห็นหลังและวิ่งมีเฟรมจริง เดินหลัง/หน้าเฟอร์นิเจอร์ซ้อนถูก ไม่มีทางเดินตันโดยไม่ตั้งใจ
- คลิกตาแมวเข้าสู่มุม first person เต็มจอ เห็นใบหน้า; สแกนมีเอฟเฟกต์และหลักฐานด้านซ้าย; เลือกตรวจแล้ว simulation เปลี่ยนครั้งเดียวตามกติกา
- รับ/ปฏิเสธแขกแล้วภาพในฐานและ simulation ตรงกัน กลับเข้าออกหน้าตรวจไม่สร้างแขกหรือของซ้ำ
- อาหารบนชั้นและมื้ออาหารตรงกับ inventory; HUD ไม่มีเลขต้นทุนยัดใส่ทุกปุ่ม แต่มีคำเตือนความเสี่ยงที่เข้าใจได้
- ภาษาไทย/อังกฤษไม่ล้นการ์ดที่ 1920×1080 และ 1280×720; ตรวจ hover/focus/Esc/เปิดปิดซ้ำ และลด motion
- รัน tests ที่เกี่ยวข้องกับทรัพยากร แขก และเวลา รวมถึงตรวจจริงใน Play mode; ใช้การทดสอบเดิมและเพิ่มเฉพาะ regression ที่มีความหมาย
- รายงานไฟล์ที่แก้ หลักฐานที่ทดสอบจริง สิ่งที่ยังเป็นต้นแบบ และข้อจำกัด ห้ามอ้างว่า compile ผ่านหรือภาพสวยขึ้นโดยไม่มีหลักฐาน

## สกิลที่แนะนำให้ใช้ตามขั้นตอน

ไม่จำเป็นต้องเปิดทุกสกิลพร้อมกัน ให้เลือกตามงานและอ่าน SKILL.md จริงก่อนใช้

1. `unity-project-audit` — ตรวจเวอร์ชัน renderer โครงสร้าง และสภาพโปรเจกต์
2. `game-design-puzzle-balancing` — วางวงจรสังเกต → ตรวจ → ตัดสินใจ → ผลที่เรียนรู้ได้
3. `pixel-art-game-pipeline` — ตั้งมาตรฐานห้องหลายชั้น sprite ทิศทาง pivot และเฟรม
4. `unity-environment-level-design` — องค์ประกอบห้อง ระยะลึก ทางเดิน และของบัง
5. `unity-workbench:unity-feature-implementation` — ผูกฟีเจอร์เข้าระบบเดิมอย่างเป็นขั้นตอน
6. `unity-uitoolkit` — HUD การ์ด hover/focus overlay และ typography ไทย
7. `unity-vfx-audio-game-feel` — เอฟเฟกต์สแกน เสียงเคาะ feedback การกิน/ซ่อม และการ์ด
8. `imagegen` — concept art / portrait / texture ใหม่ที่จำเป็น โดยตรวจสิทธิ์และความสอดคล้องก่อนนำเข้า
9. `coding-debug-verification` และ `unity-workbench:unity-build-validation` — ตรวจ compile, tests, Play mode และหลักฐานจริง
10. `git-github-collaboration` — ปกป้องงานแก้ค้างและงานเพื่อน ห้ามเผยแพร่เอง

หากมี Unity MCP ให้ตรวจการเชื่อมต่อก่อนใช้สกิล automation หากไม่มีให้ใช้ Editor/CLI ที่มีจริง และอย่าอ้างว่าแก้ scene ผ่าน MCP แล้ว
